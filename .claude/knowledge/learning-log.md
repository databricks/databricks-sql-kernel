# Engineer-bot learning log — databricks-sql-kernel

Durable, reusable engineering learnings distilled from merged PRs by the
engineer-bot retrospective flow (`engineer-bot-learning.yml` →
`databricks_bot_engine.engineer_bot.retrospective`). Each entry is a **Context** +
**Rule** pair; the Rule is written to be greppable so future engineer-bot runs can
surface it. Entries run oldest→newest.

Both bots also read this file as repo conventions (`.claude/knowledge/**` is always
injected into the system prompt), so a logged Rule feeds forward into future
author, follow-up, and review runs.

## Entries

### 2026-08-14: learnings since 2026-08-13T07:50:36Z
- **Context:** PR #241 (mandatory OIDC token exchange) added `FederationProvider`/`CacheEntry` with `#[derive(Debug)]`; both a review bot and a human reviewer flagged that the derived impl prints the raw source JWT and the minted in-house `access_token` in the clear, bypassing the redaction that `AuthConfig` in `src/config.rs` hand-writes.
  **Rule:** Never `#[derive(Debug)]` on a type that transitively holds auth tokens/secrets (access tokens, client secrets, JWTs) — hand-write a `Debug` that redacts the secret fields, matching the repo's existing `AuthConfig` redaction convention, and add a test asserting tokens never appear in Debug output.
- **Context:** PR #246 collapsed an ODBC empty `table_types` CSV to `None` because `Some(&[])` now means match-NONE (hiveserver2 #83 reversed the earlier empty==null reading); PR #248's reviewer flagged the mirror case where a C caller passing `""` records `Some("")` and silently selects SP-wide WIF instead of the documented "unset" BYOT branch.
  **Rule:** At C-ABI/ODBC boundaries an empty string or empty collection is NOT the same as absent — `required_str`/CSV splits yield `Some("")`/`Some(&[])`, distinct from `None`. Explicitly collapse empty→`None` (or reject it) so the documented "unset" semantics hold, and lock the collapse with a test since downstream match-arms treat `Some(empty)` differently from `None`.
- **Context:** PRs #247 and #241 threaded U2M OAuth defaults; reviewers repeatedly flagged that overriding the OAuth client without pinning its matching scopes and redirect port inherits the kernel's defaults for a *different* registered app — e.g. `databricks-sql-python` requesting `all-apis` → `access_denied`, or the `8030` default port → `redirect_uri_mismatch`.
  **Rule:** U2M OAuth `{client_id, scopes, redirect_port}` are a coupled bundle tied to one registered IdP app — when a binding overrides `client_id`, it must also pin the scopes and redirect port for that app (only when the caller relies on the default client); never half-override the bundle.
- **Context:** PR #247's reviewer caught that `napi/index.d.ts` is auto-generated from the Rust doc comments on `ConnectionOptions`, so a doc-only edit to `napi/src/database.rs` that skipped regenerating the `.d.ts` propagated stale values (port `8020`, wrong scopes) into the committed types; the fix hand-synced both sides.
  **Rule:** `napi/index.d.ts` is generated from the Rust doc comments in `napi/src/database.rs` — any change to those docs (or to defaults they describe) must regenerate or hand-sync `index.d.ts` in the same PR, or the two silently drift.

### 2026-08-18: learnings since 2026-08-17T07:37:07Z
- **Context:** PR #250 (telemetry design) and PR #184 (README quick-start) — reviewers flagged that public `#[non_exhaustive]` config structs (`TelemetryConfig`, `HttpConfig`) can't be built from the pyo3/napi binding crates, which are separate crates.
  **Rule:** A `#[non_exhaustive]` public struct cannot be built with struct-literal syntax from another crate — including `..Default::default()` functional-update (hard E0639) — so every `#[non_exhaustive]` config needs a `new()`/builder (repo convention, e.g. `ConnectionConfig::new`) or callers must use construct-then-mutate; remember pyo3/napi/C-ABI bindings are external crates subject to this.
- **Context:** PR #257 replaced the single U2M `redirect_port` with an ordered `redirect_ports` candidate list for the OAuth browser flow.
  **Rule:** A U2M OAuth callback port must be a static port pre-registered as the IdP's `redirect_uri`: port `0` binds an OS-ephemeral port that can never match (reject it), and `databricks-sql-python` registers a *discrete* set (`8020`/`8025`), not a contiguous range — so never auto-walk `+N`; require caller-supplied exact ports. Exception: the default in-house app normalizes loopback redirects by dropping the port (RFC 8252 §7.3), so any `http://localhost:{port}` works only for that default client.
- **Context:** PR #184 (connection-parameter reference) — a reviewer claimed `CAN_CLOUD_DOWNLOAD` was an allowlisted server-side `session_conf` key; the code deliberately excludes it (regression tripwire `session_conf_filter_drops_can_cloud_download`, issue #196).
  **Rule:** CloudFetch is selected via the SEA request `disposition`, NOT a `session_conf` key — `CAN_CLOUD_DOWNLOAD`/`can_cloud_download` is intentionally not in `SESSION_CONF_ALLOWLIST` and any caller-supplied value is silently dropped; expose the toggle only through `ResultConfig::cloudfetch_enabled` (and the client-only `cloudfetch_enabled` key), never as a server conf.
- **Context:** PR #184 — the README quick-start had two compile errors (E0639 `#[non_exhaustive]` construction, missing `ExecutedStatementHandle` trait import) plus rustdoc `#`-hidden lines rendering literally on GitHub; CI never caught them.
  **Rule:** Fenced ```rust blocks in README.md are NOT compiled by `cargo test` unless the file is wired in via `#![doc = include_str!("../README.md")]`; treat README/markdown examples as untested — manually verify imports (traits in scope), `#[non_exhaustive]` construction, and drop the rustdoc `#`-hidden-line convention since GitHub shows those lines verbatim.
- **Context:** PR #257 pyo3 rename thread — engineer-bot repeatedly replied "no code change needed," insisting both `redirect_port` and `redirect_ports` kwargs were present, while the actual HEAD signature exposed only `redirect_ports`; the reviewer had to re-fetch and push back across several rounds before the fix landed.
  **Rule:** Before answering a reviewer's claim about the current diff/signature with "no change needed / already present," re-read the file at HEAD and quote the exact current lines — do not rely on a remembered or partial read of the working tree; asserting a symbol is present/absent from stale context burns review rounds.

### 2026-08-19: learnings since 2026-08-18T07:28:49Z
- **Context:** The telemetry model contract (PR #255/#266) hand-serializes the SQL driver telemetry envelope with serde; a reviewer noted that the reference C# ADBC driver serializes the inner `sql_driver_log` (`OssSqlDriverTelemetryLog`) subtree via protobuf `JsonFormatter`, which encodes `int64` as JSON *strings* (`"25"`), while the outer envelope (`workspace_id`, `timestamp_millis`, `upload_time`) uses plain JSON *numbers* — and JDBC emits the same latency field as a number. serde emits every `i64` as a bare number.
  **Rule:** When mirroring the Databricks SQL-driver telemetry envelope, the int64 JSON encoding is not uniform — proto-subtree int64 fields follow proto3 JSON (quoted strings) while the hand-written wrapper fields stay numeric; don't blanket-stringify or blanket-number, confirm each field's representation against the backend/reference and pin it with a serialization test (field-name-only assertions miss number-vs-string divergence).
- **Context:** In the connection-telemetry runtime (PR #256/#266/#267) `sanitize_error` populated the telemetry envelope's `DriverErrorInfo.stack_trace` field with `error.sql_state` (a 5-char SQLSTATE like `42P01`); reviewers repeatedly flagged the semantic mismatch, and maintainers confirmed ADBC deliberately omits `stack_trace` for security while JDBC passes messages.
  **Rule:** Don't overload a telemetry-envelope field with unrelated data to make it non-empty — a field named `stack_trace` must carry trace/diagnostic text (or be `None`), never a SQLSTATE code; match each envelope field's meaning to the reference ADBC/JDBC proto so downstream consumers aren't misled.
- **Context:** PR #259 refactored SEA statement-failure SQLSTATE extraction to read only the new top-level `status.sql_state`, dropping the prior fallback rungs (nested `status.error.sql_state` and the `"SQLSTATE: XXXXX"` message parse). Reviewers noted the added/updated wiremock `failed_body` fixtures set *both* the new top-level field *and* the message suffix, so the tests passed regardless of whether the dropped fallbacks still existed — the regression was invisible to the suite.
  **Rule:** When a value can be sourced from multiple wire locations and a change narrows which locations are consulted, fixtures that populate all locations at once cannot catch a dropped-fallback regression; add a test that exercises each source in isolation (e.g. a FAILED body carrying SQLSTATE only in the legacy/nested field or only in the message text).
- **Context:** In the telemetry model PR (#255/#266), reviewers and maintainers found several `DriverConnectionParameters` fields whose Rust types were copied from the C# ADBC `.proto` port and diverged from the authoritative server-side definition (e.g. `azure_workspace_resource_id`, `azure_tenant_id`, `jwt_key_file`, `jwt_algorithm` typed `Option<String>` vs proto `bool`; `allowed_volume_ingestion_paths` `Option<String>` vs proto `int64`). A maintainer directed using the server-side `universe` proto as source of truth.
  **Rule:** When porting telemetry/protocol model structs, treat the server-side `universe` proto as the source of truth (not a sibling driver's C#/JDBC port) and verify every field's type against it — downstream driver ports can and do carry type drift.

### 2026-08-20: learnings since 2026-08-19T07:29:09Z
- **Context:** PR #261 added a telemetry client cached per-host in a process-global manager; `TelemetryClientLease` had no `Drop` and its refcount was decremented only via an async `release()` reachable solely through `Session::close()`. Sessions dropped without `close()` leaked the `Arc<TelemetryClient>` and its background timer task forever.
  **Rule:** A refcounted/background resource (timer task, pooled client) whose cleanup lives in a `close()`/`release()` that consumes `self` will leak whenever a holder is merely dropped — give the guard a `Drop` impl that fires a best-effort fire-and-forget release (mirroring the session's `initiate_delete()` pattern), never rely on the explicit-close path alone.
- **Context:** PR #261's telemetry exporter called `reqwest::Client::new()` on every batch export just to build a `Request`, then dispatched through the shared `DatabricksHttpClient`; the throwaway client's pool/TLS were never used, and `reqwest::Client::new()` panics if the TLS backend/resolver fails to initialize.
  **Rule:** Never construct `reqwest::Client::new()` per request — it allocates a fresh connection pool + TLS state and panics on TLS-init failure (turning a recoverable I/O path into a panic); build requests from the existing shared client's builder (e.g. `http_client.inner()`) and reuse the pooled client.
- **Context:** PR #261's telemetry integration tests injected a `CapturingTelemetryExporter`, which set `bypass_cache=true` and short-circuited the real `DatabricksTelemetryExporter`, so URL construction, JSON serialization, `RequestType` retry wiring, and response handling for the new `/telemetry-ext` POST were never exercised.
  **Rule:** Injecting a fake/capturing exporter or transport bypasses the real HTTP dispatch path — a protocol change (new endpoint, request-building, retry classification) needs a wiremock test driving the real exporter against a mock endpoint, asserting the POST path/body and fail-open behavior; an in-memory fake proves nothing about the wire.
- **Context:** PR #261's `TelemetryClientManager` is a process-global singleton keyed on host only; the first session to a host builds the exporter capturing *its* `Arc<DatabricksHttpClient>` (and auth token), so every later session to the same host exports telemetry through the first session's credentials, and its per-session config is silently dropped.
  **Rule:** A per-host (or otherwise identity-blind) global client cache captures the first caller's credentials/config for the life of the host entry — later callers with different auth get cross-principal mis-attribution and fail-open on token expiry; key such caches on credential/identity, or document first-writer-wins explicitly, whenever the cached transport carries per-session auth.
- **Context:** In PR #249 `build_client_assertion()` (RSA/EC JWT signing) was called at the top of `get_auth_header`, which runs on every outbound request via `execute_impl`, but the signed assertion is consumed only when a token refresh actually fires — so the fresh-token fast path signed and discarded a JWT on every query.
  **Rule:** `auth_header()` runs per-request on the hot path; expensive crypto (JWT/assertion signing) belongs inside the token-refresh closure (capturing `Arc` key + cheaply-cloned claim inputs) so it runs only on the empty/expired/stale-refresh paths, never once per query.
- **Context:** In PR #249 an auth path wrote a manual `if !status.is_success()` branch after `http_client.execute_without_auth(...).await?` to surface the server error body with JDBC-parity wording, but that branch was unreachable — `execute_without_auth` returns `Ok` only for 2xx and `Err(http_error(...))` for every non-2xx status, so the body-reading code and its comment were dead.
  **Rule:** The HTTP client's `execute*` methods return `Ok` only on success and `Err` for non-2xx — code after a `?` cannot see a non-success response, so any manual non-success branch there is dead; to include the server response body in the error, capture it inside the client's error path, not at the call site.
- **Context:** PR #249 decrypted PKCS#8 private keys into plaintext PEM `String`s (`decrypt_pkcs8_pem`, `read_key_pem`) that were dropped normally, leaving key material in freed heap memory, even though the repo already pulls in `zeroize` specifically to wipe derived key material on drop.
  **Rule:** Decrypted/parsed private-key material must be wrapped in a zeroizing container (or explicitly zeroized before drop) to match the repo's key-handling posture; re-encoding a decrypted key to an unencrypted PEM `String` and dropping it normally leaves the plaintext lingering in freed heap.
- **Context:** PR #249 deliberately pinned `jsonwebtoken` to 9.x (built-in `ring` backend) because 10.x forces an explicit crypto backend whose `rust_crypto` option pulls `rsa` (RUSTSEC-2023-0071, Marvin attack) into the runtime graph; the `deny.toml`/`osv-scanner` ignore for that advisory is global-by-ID and keeps `rsa` acceptable only while it stays dev-only.
  **Rule:** Keep `rsa` (RUSTSEC-2023-0071) out of the runtime dependency graph — it is tolerated only as a dev-dependency; avoid crypto-lib upgrades (e.g. jsonwebtoken 10.x `rust_crypto` backend) that pull it into shipped code, since the advisory ignore is unconditional and would silently suppress the CI gate once `rsa` becomes a runtime dep.
- **Context:** PRs #275 and #249 both surfaced that JWT client-assertion M2M (`OAuthM2mJwt`) against an external-IdP-backed workspace (e.g. Entra ID for Azure Databricks) requires a `token_url` override because Databricks-native OIDC discovery does not advertise the `private_key_jwt` grant; the pyo3 and C bindings exposed the override but napi initially hardcoded it to `None`, and only one of the two changed auth arms got test coverage.
  **Rule:** JWT/private-key M2M cannot rely on OIDC discovery (Databricks-native OIDC omits `private_key_jwt`) — a token-endpoint override must be exposed and threaded through *every* FFI binding (napi/pyo3/C), and when threading a new arg into multiple auth arms, add a test asserting it reaches the kernel config on each arm, not just one.
