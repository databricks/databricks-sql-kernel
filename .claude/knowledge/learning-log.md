# Engineer-bot learning log — databricks-sql-kernel

Durable, reusable engineering learnings distilled from merged PRs by the
engineer-bot retrospective flow (`engineer-bot-learning.yml` →
`databricks_bot_engine.engineer_bot.retrospective`). Each entry is a **Context** +
**Rule** pair; the Rule is written to be greppable so future engineer-bot runs can
surface it. Entries run oldest→newest.

Both bots also read this file as repo conventions (`.claude/knowledge/**` is always
injected into the system prompt), so a logged Rule feeds forward into future
author, follow-up, and review runs.

### 2026-08-14: learnings since 2026-08-13T07:50:36Z
- **Context:** PR #241 (mandatory OIDC token exchange) added `FederationProvider`/`CacheEntry` with `#[derive(Debug)]`; both a review bot and a human reviewer flagged that the derived impl prints the raw source JWT and the minted in-house `access_token` in the clear, bypassing the redaction that `AuthConfig` in `src/config.rs` hand-writes.
  **Rule:** Never `#[derive(Debug)]` on a type that transitively holds auth tokens/secrets (access tokens, client secrets, JWTs) — hand-write a `Debug` that redacts the secret fields, matching the repo's existing `AuthConfig` redaction convention, and add a test asserting tokens never appear in Debug output.
- **Context:** PR #246 collapsed an ODBC empty `table_types` CSV to `None` because `Some(&[])` now means match-NONE (hiveserver2 #83 reversed the earlier empty==null reading); PR #248's reviewer flagged the mirror case where a C caller passing `""` records `Some("")` and silently selects SP-wide WIF instead of the documented "unset" BYOT branch.
  **Rule:** At C-ABI/ODBC boundaries an empty string or empty collection is NOT the same as absent — `required_str`/CSV splits yield `Some("")`/`Some(&[])`, distinct from `None`. Explicitly collapse empty→`None` (or reject it) so the documented "unset" semantics hold, and lock the collapse with a test since downstream match-arms treat `Some(empty)` differently from `None`.
- **Context:** PRs #247 and #241 threaded U2M OAuth defaults; reviewers repeatedly flagged that overriding the OAuth client without pinning its matching scopes and redirect port inherits the kernel's defaults for a *different* registered app — e.g. `databricks-sql-python` requesting `all-apis` → `access_denied`, or the `8030` default port → `redirect_uri_mismatch`.
  **Rule:** U2M OAuth `{client_id, scopes, redirect_port}` are a coupled bundle tied to one registered IdP app — when a binding overrides `client_id`, it must also pin the scopes and redirect port for that app (only when the caller relies on the default client); never half-override the bundle.
- **Context:** PR #247's reviewer caught that `napi/index.d.ts` is auto-generated from the Rust doc comments on `ConnectionOptions`, so a doc-only edit to `napi/src/database.rs` that skipped regenerating the `.d.ts` propagated stale values (port `8020`, wrong scopes) into the committed types; the fix hand-synced both sides.
  **Rule:** `napi/index.d.ts` is generated from the Rust doc comments in `napi/src/database.rs` — any change to those docs (or to defaults they describe) must regenerate or hand-sync `index.d.ts` in the same PR, or the two silently drift.

### 2026-08-18: learnings since 2026-08-17T07:37:07Z
- **Context:** PR #250 (telemetry design) and PR #184 (README quick-start) — reviewers flagged that public `#[non_exhaustive]` config structs (`TelemetryConfig`, `HttpConfig`) can't be built from the pyo3/napi binding crates, which are separate crates.
  **Rule:** A `#[non_exhaustive]` public struct cannot be built with struct-literal syntax from another crate — including `..Default::default()` functional-update (hard E0639) — so every `#[non_exhaustive]` config needs a `new()`/builder (repo convention, e.g. `ConnectionConfig::new`) or callers must use construct-then-mutate; remember pyo3/napi/C-ABI bindings are external crates subject to this.
- **Context:** PR #257 replaced the single U2M `redirect_port` with an ordered `redirect_ports` candidate list for the OAuth browser flow.
  **Rule:** A U2M OAuth callback port must be a static port pre-registered as the IdP's `redirect_uri`: port `0` binds an OS-ephemeral port that can never match (reject it), and `databricks-sql-python` registers a *discrete* set (`8020`/`8025`), not a contiguous range — so never auto-walk `+N`; require caller-supplied exact ports. Exception: the default in-house app normalizes loopback redirects by dropping the port (RFC 8252 §7.3), so any `http://localhost:{port}` works only for that default client.
- **Context:** PR #184 (connection-parameter reference) — a reviewer claimed `CAN_CLOUD_DOWNLOAD` was an allowlisted server-side `session_conf` key; the code deliberately excludes it (regression tripwire `session_conf_filter_drops_can_cloud_download`, issue #196).
  **Rule:** CloudFetch is selected via the SEA request `disposition`, NOT a `session_conf` key — `CAN_CLOUD_DOWNLOAD`/`can_cloud_download` is intentionally not in `SESSION_CONF_ALLOWLIST` and any caller-supplied value is silently dropped; expose the toggle only through `ResultConfig::cloudfetch_enabled` (and the client-only `cloudfetch_enabled` key), never as a server conf.
- **Context:** PR #184 — the README quick-start had two compile errors (E0639 `#[non_exhaustive]` construction, missing `ExecutedStatementHandle` trait import) plus rustdoc `#`-hidden lines rendering literally on GitHub; CI never caught them.
  **Rule:** Fenced ```rust blocks in README.md are NOT compiled by `cargo test` unless the file is wired in via `#![doc = include_str!("../README.md")]`; treat README/markdown examples as untested — manually verify imports (traits in scope), `#[non_exhaustive]` construction, and drop the rustdoc `#`-hidden-line convention since GitHub shows those lines verbatim.
- **Context:** PR #257 pyo3 rename thread — engineer-bot repeatedly replied "no code change needed," insisting both `redirect_port` and `redirect_ports` kwargs were present, while the actual HEAD signature exposed only `redirect_ports`; the reviewer had to re-fetch and push back across several rounds before the fix landed.
  **Rule:** Before answering a reviewer's claim about the current diff/signature with "no change needed / already present," re-read the file at HEAD and quote the exact current lines — do not rely on a remembered or partial read of the working tree; asserting a symbol is present/absent from stale context burns review rounds.

### 2026-08-19: learnings since 2026-08-18T07:28:49Z
- **Context:** The telemetry model contract (PR #255/#266) hand-serializes the SQL driver telemetry envelope with serde; a reviewer noted that the reference C# ADBC driver serializes the inner `sql_driver_log` (`OssSqlDriverTelemetryLog`) subtree via protobuf `JsonFormatter`, which encodes `int64` as JSON *strings* (`"25"`), while the outer envelope (`workspace_id`, `timestamp_millis`, `upload_time`) uses plain JSON *numbers* — and JDBC emits the same latency field as a number. serde emits every `i64` as a bare number.
  **Rule:** When mirroring the Databricks SQL-driver telemetry envelope, the int64 JSON encoding is not uniform — proto-subtree int64 fields follow proto3 JSON (quoted strings) while the hand-written wrapper fields stay numeric; don't blanket-stringify or blanket-number, confirm each field's representation against the backend/reference and pin it with a serialization test (field-name-only assertions miss number-vs-string divergence).
- **Context:** In the connection-telemetry runtime (PR #256/#266/#267) `sanitize_error` populated the telemetry envelope's `DriverErrorInfo.stack_trace` field with `error.sql_state` (a 5-char SQLSTATE like `42P01`); reviewers repeatedly flagged the semantic mismatch, and maintainers confirmed ADBC deliberately omits `stack_trace` for security while JDBC passes messages.
  **Rule:** Don't overload a telemetry-envelope field with unrelated data to make it non-empty — a field named `stack_trace` must carry trace/diagnostic text (or be `None`), never a SQLSTATE code; match each envelope field's meaning to the reference ADBC/JDBC proto so downstream consumers aren't misled.
- **Context:** PR #259 refactored SEA statement-failure SQLSTATE extraction to read only the new top-level `status.sql_state`, dropping the prior fallback rungs (nested `status.error.sql_state` and the `"SQLSTATE: XXXXX"` message parse). Reviewers noted the added/updated wiremock `failed_body` fixtures set *both* the new top-level field *and* the message suffix, so the tests passed regardless of whether the dropped fallbacks still existed — the regression was invisible to the suite.
  **Rule:** When a value can be sourced from multiple wire locations and a change narrows which locations are consulted, fixtures that populate all locations at once cannot catch a dropped-fallback regression; add a test that exercises each source in isolation (e.g. a FAILED body carrying SQLSTATE only in the legacy/nested field or only in the message text).
- **Context:** In the telemetry model PR (#255/#266), reviewers and maintainers found several `DriverConnectionParameters` fields whose Rust types were copied from the C# ADBC `.proto` port and diverged from the authoritative server-side definition (e.g. `azure_workspace_resource_id`, `azure_tenant_id`, `jwt_key_file`, `jwt_algorithm` typed `Option<String>` vs proto `bool`; `allowed_volume_ingestion_paths` `Option<String>` vs proto `int64`). A maintainer directed using the server-side `universe` proto as source of truth.
  **Rule:** When porting telemetry/protocol model structs, treat the server-side `universe` proto as the source of truth (not a sibling driver's C#/JDBC port) and verify every field's type against it — downstream driver ports can and do carry type drift.

### 2026-08-20: learnings since 2026-08-19T07:29:09Z
- **Context:** PR #261 added a telemetry client cached per-host in a process-global manager; `TelemetryClientLease` had no `Drop` and its refcount was decremented only via an async `release()` reachable solely through `Session::close()`. Sessions dropped without `close()` leaked the `Arc<TelemetryClient>` and its background timer task forever.
  **Rule:** A refcounted/background resource (timer task, pooled client) whose cleanup lives in a `close()`/`release()` that consumes `self` will leak whenever a holder is merely dropped — give the guard a `Drop` impl that fires a best-effort fire-and-forget release (mirroring the session's `initiate_delete()` pattern), never rely on the explicit-close path alone.
- **Context:** PR #261's telemetry exporter called `reqwest::Client::new()` on every batch export just to build a `Request`, then dispatched through the shared `DatabricksHttpClient`; the throwaway client's pool/TLS were never used, and `reqwest::Client::new()` panics if the TLS backend/resolver fails to initialize.
  **Rule:** Never construct `reqwest::Client::new()` per request — it allocates a fresh connection pool + TLS state and panics on TLS-init failure (turning a recoverable I/O path into a panic); build requests from the existing shared client's builder (e.g. `http_client.inner()`) and reuse the pooled client.
- **Context:** PR #261's telemetry integration tests injected a `CapturingTelemetryExporter`, which set `bypass_cache=true` and short-circuited the real `DatabricksTelemetryExporter`, so URL construction, JSON serialization, `RequestType` retry wiring, and response handling for the new `/telemetry-ext` POST were never exercised.
  **Rule:** Injecting a fake/capturing exporter or transport bypasses the real HTTP dispatch path — a protocol change (new endpoint, request-building, retry classification) needs a wiremock test driving the real exporter against a mock endpoint, asserting the POST path/body and fail-open behavior; an in-memory fake proves nothing about the wire.
- **Context:** PR #261's `TelemetryClientManager` is a process-global singleton keyed on host only; the first session to a host builds the exporter capturing *its* `Arc<DatabricksHttpClient>` (and auth token), so every later session to the same host exports telemetry through the first session's credentials, and its per-session config is silently dropped.
  **Rule:** A per-host (or otherwise identity-blind) global client cache captures the first caller's credentials/config for the life of the host entry — later callers with different auth get cross-principal mis-attribution and fail-open on token expiry; key such caches on credential/identity, or document first-writer-wins explicitly, whenever the cached transport carries per-session auth.
- **Context:** In PR #249 `build_client_assertion()` (RSA/EC JWT signing) was called at the top of `get_auth_header`, which runs on every outbound request via `execute_impl`, but the signed assertion is consumed only when a token refresh actually fires — so the fresh-token fast path signed and discarded a JWT on every query.
  **Rule:** `auth_header()` runs per-request on the hot path; expensive crypto (JWT/assertion signing) belongs inside the token-refresh closure (capturing `Arc` key + cheaply-cloned claim inputs) so it runs only on the empty/expired/stale-refresh paths, never once per query.
- **Context:** In PR #249 an auth path wrote a manual `if !status.is_success()` branch after `http_client.execute_without_auth(...).await?` to surface the server error body with JDBC-parity wording, but that branch was unreachable — `execute_without_auth` returns `Ok` only for 2xx and `Err(http_error(...))` for every non-2xx status, so the body-reading code and its comment were dead.
  **Rule:** The HTTP client's `execute*` methods return `Ok` only on success and `Err` for non-2xx — code after a `?` cannot see a non-success response, so any manual non-success branch there is dead; to include the server response body in the error, capture it inside the client's error path, not at the call site.
- **Context:** PR #249 decrypted PKCS#8 private keys into plaintext PEM `String`s (`decrypt_pkcs8_pem`, `read_key_pem`) that were dropped normally, leaving key material in freed heap memory, even though the repo already pulls in `zeroize` specifically to wipe derived key material on drop.
  **Rule:** Decrypted/parsed private-key material must be wrapped in a zeroizing container (or explicitly zeroized before drop) to match the repo's key-handling posture; re-encoding a decrypted key to an unencrypted PEM `String` and dropping it normally leaves the plaintext lingering in freed heap.
- **Context:** PR #249 deliberately pinned `jsonwebtoken` to 9.x (built-in `ring` backend) because 10.x forces an explicit crypto backend whose `rust_crypto` option pulls `rsa` (RUSTSEC-2023-0071, Marvin attack) into the runtime graph; the `deny.toml`/`osv-scanner` ignore for that advisory is global-by-ID and keeps `rsa` acceptable only while it stays dev-only.
  **Rule:** Keep `rsa` (RUSTSEC-2023-0071) out of the runtime dependency graph — it is tolerated only as a dev-dependency; avoid crypto-lib upgrades (e.g. jsonwebtoken 10.x `rust_crypto` backend) that pull it into shipped code, since the advisory ignore is unconditional and would silently suppress the CI gate once `rsa` becomes a runtime dep.
- **Context:** PRs #275 and #249 both surfaced that JWT client-assertion M2M (`OAuthM2mJwt`) against an external-IdP-backed workspace (e.g. Entra ID for Azure Databricks) requires a `token_url` override because Databricks-native OIDC discovery does not advertise the `private_key_jwt` grant; the pyo3 and C bindings exposed the override but napi initially hardcoded it to `None`, and only one of the two changed auth arms got test coverage.
  **Rule:** JWT/private-key M2M cannot rely on OIDC discovery (Databricks-native OIDC omits `private_key_jwt`) — a token-endpoint override must be exposed and threaded through *every* FFI binding (napi/pyo3/C), and when threading a new arg into multiple auth arms, add a test asserting it reaches the kernel config on each arm, not just one.

### 2026-08-21: learnings since 2026-08-20T07:29:39Z
- **Context:** PR #279 added `kernel_session_test` (C ABI) / `Session::test_connection`, a `SELECT 1` liveness probe a host wires to `SQL_ATTR_CONNECTION_DEAD`; the reviewer noted the failure tests only asserted `!= Success` / `expect_err` and never pinned the returned status.
  **Rule:** When a status/error category is itself the contract a host branches on (e.g. connection-dead → `Unavailable`/`NetworkError`/`Timeout` vs auth/parse errors), assert the concrete `KernelStatusCode` / `Error` category in tests, not merely "not Success" — a test that accepts any error still passes when the mapping silently regresses to the wrong category.
- **Context:** PR #269 exposed `Statement.set_row_limit`; the reviewer flagged that JDBC treats `maxRows == 0` as *unlimited* and omits the wire field when `<= 0`, while the kernel forwards `row_limit` verbatim into the SEA request (an explicit `row_limit: 0`).
  **Rule:** Numeric cap/limit parameters diverge from the JDBC connector's sentinel convention — JDBC uses `0`/negative to mean "no limit" and omits the field on the wire, whereas the kernel passes the value through unvalidated. When adding such a knob, document the `0`/negative boundary semantics and test them against a live warehouse rather than assuming JDBC-equivalent behavior.
- **Context:** PR #263 (`azure-sp-m2m`) mints the Azure management token that backs the `X-Databricks-Azure-SP-Management-Token` header; the design pins it to the Entra **v1.0** `resource=` grant so the `aud` is `https://management.core.windows.net/` verbatim (trailing slash included), because the v2.0 `.default` form drops the slash and the control plane rejects it.
  **Rule:** For the Azure management-token add-on, use the Entra v1.0 `resource=` grant (not the v2.0 `{resource}/.default` scope) so the audience keeps its exact trailing slash; and gate the management-token fetch + both `X-Databricks-Azure-*` headers on `azure_workspace_resource_id` being set (JDBC parity, `if (resourceId != null)`) so a plain workspace-member SP is never forced through an ARM exchange it cannot complete.
- **Context:** PR #263 round-trips the foreign Entra-issued token through the workspace `/oidc/v1/token` federation exchange with a "non-breaking fallback"; the reviewer noted the fallback keys off *failure* and asked for a wiremock matrix covering non-clean failure modes.
  **Rule:** A fallback that only triggers on a clean error will silently ship a broken result on a 200-with-unusable-token, a hang/timeout, or a partial response — when a novel/unproven exchange sits on the request hot path, test every failure mode explicitly (not just a 4xx) and back it with an `#[ignore]`d live E2E, since a mock cannot prove the real endpoint accepts the assertion.

### 2026-08-22: learnings since 2026-08-21T07:31:26Z
- **Context:** PR #277 fixed a Windows ODBC DriverManager teardown crash in the C ABI (#276). The C ABI owns a process-wide tokio runtime and previously drove every entry point via `Runtime::block_on` on the foreign caller thread.
  **Rule:** In a C ABI that owns its own tokio runtime, drive futures by `spawn`ing onto the runtime's own worker threads and blocking on a plain std channel for the result — never `Runtime::block_on` on the foreign caller thread. `block_on` registers tokio's runtime-context TLS on a thread the kernel doesn't own (ODBC/Go caller threads); when that thread is torn down on Windows/MSVC the guard drops out of order and trips the "EnterGuard dropped out of order" panic / "allocator may not use TLS with destructors" abort.
- **Context:** PR #277 — converting C-ABI metadata entry points so their futures are `spawn`ed onto runtime worker threads (which requires the future and its output to be `Send`).
  **Rule:** When an FFI async future is moved onto runtime worker threads, marshal raw C-string pointers (which are `!Send`) into owned Rust values (`opt_ident`/`opt_str`/etc.) synchronously on the caller thread BEFORE the `async move` block, and capture only those owned values — otherwise the future captures the `!Send` raw pointers and won't compile / would smuggle non-thread-safe pointers across threads.
- **Context:** PR #277 — a statically-linked kernel running detached tokio worker threads inside an ODBC driver DLL that the DriverManager loads and unloads across connections.
  **Rule:** When a static-linked kernel spawns detached runtime worker threads that outlive a single connection inside a host-loaded DLL, pin the containing module (`GetModuleHandleExW` with `FROM_ADDRESS | PIN`, passing the address of a function in the kernel's own code) so the host's `FreeLibrary` cannot unmap code out from under live threads. Since the pin is load-bearing, check its return value and log on failure rather than discarding it — a silent pin failure reintroduces the exact crash with no diagnostic trail.
- **Context:** PR #262 wired telemetry/driver-system config through the napi binding; reviewers repeatedly flagged the ms-duration/size knobs as `Option<u32>` versus the PyO3 (`u64`/`usize`) and C-ABI (`u64`) surfaces.
  **Rule:** In napi-rs bindings, type millisecond-duration and size knobs as `u32` (napi-rs serializes `u32` as a plain JS `number`) rather than `u64`/`usize`, which surface to JS callers as `BigInt` — a worse ergonomic. This intentionally diverges from the PyO3/C-ABI `u64` surfaces (Python ints are unbounded, FFI wants fixed width); document the divergence and the resulting ~49.7-day ceiling inline, since the value is widened via `u64::from(v)` before use and the cap is irrelevant for real intervals.

### 2026-08-23: learnings since 2026-08-22T07:27:43Z
- **Context:** PR #272 added statement-execution telemetry to the SEA transport; a reviewer caught that `telemetry_is_compressed` reported `true` for any non-empty `result_compression` codec, while the decode path (`CompressionCodec::from_manifest`) treats only `"LZ4_FRAME"` as compressed and maps everything else to `None`.
  **Rule:** Derive telemetry/observability flags from the SAME parser the real code path uses (e.g. `CompressionCodec::from_manifest`) rather than re-deriving them with an ad-hoc check — independent classification logic silently drifts from decode behavior and misreports.
- **Context:** PR #272's async statement telemetry uses a one-shot idempotent `finalize()` (latched on an `AtomicBool` swap). Reviewers found it was called on RESUMABLE conditions — the internal poll-timeout in `await_result()` and a premature `fetch_result()` returning `InvalidState` ("not terminal yet") — so the first (recoverable) call latches a failure event and the later real terminal outcome becomes a no-op.
  **Rule:** Never fire one-shot/idempotent terminal telemetry (or any latched finalize) on a resumable or non-terminal error; defer finalization to the genuine terminal outcome, and make sure the deferred branch's cancel/cleanup behavior agrees with the recorded state (a branch that fire-and-forget cancels the statement must record the failure, not defer to a later success).
- **Context:** PR #272's sync `execute()` always finalizes exactly one telemetry event, but the async `ExecutedAsyncStatement` only finalized via terminal consumption (`await_result`/`fetch_result`/failed `status()`); submit-then-drop and status-only-then-drop handles emitted no `EXECUTE_STATEMENT_ASYNC` event even though the server-side statement was created and closed on Drop.
  **Rule:** To guarantee "one terminal event per operation," finalize telemetry in the `Drop` impl of fire-and-forget/async handles (relying on the idempotent finalize guard to avoid double-emit) — terminal-consumption-only instrumentation silently drops abandoned and status-only lifecycles.
- **Context:** PR #272 shipped telemetry fields that no code path ever populates: `retry_count` initialized to `Some(0)` (retries live in the HTTP transport, unwired to the observer), and sync-path `n_operation_status_calls`/`operation_status_latency_millis` emitted as `Some(0)` because `record_poll` only fires on the async path. Reviewers noted consumers can't distinguish a measured 0 from an unmeasured placeholder.
  **Rule:** Emit `None`/omit telemetry fields that aren't yet wired to a real observed value rather than a constant `Some(0)`/`false` placeholder — a hard zero reads downstream as measured ("no retries", "no polls") and corrupts metrics.
- **Context:** In PR #272 the async `operation_latency_ms` stamps `started_at` at `submit()` and reads `elapsed()` at `finalize()`; for submit-and-drop / status-only handles `finalize` runs from `Drop`, so the metric measures how long the application held the handle alive, not server execution time.
  **Rule:** Anchor duration/latency telemetry to the terminal observation point (final poll/response), not to `Drop`-time finalization — Drop can be arbitrarily delayed by the caller and turns an execution-latency metric into a handle-lifetime metric.

### 2026-08-24: learnings since 2026-08-23T07:28:02Z
- **Context:** PR #278 added a `CallbackLogLayer` tracing layer whose `on_event` only calls `event.record(&mut visitor)` and ignores the `Context`, so fields attached to enclosing spans (e.g. query/statement IDs from `info_span!`) are dropped — while the existing `fmt::layer()` file/stderr path DOES surface span context, making the two sinks silently diverge.
  **Rule:** A custom `tracing` Layer that records only event fields delivers strictly less context than `fmt::layer()`; walk `ctx.event_scope()` to include enclosing-span fields (or explicitly document the sink forwards only "event fields", never "structured fields") so consumers relying on span-scoped IDs aren't misled.
- **Context:** PR #278's `kernel_init_logging_callback` documents "Success means this exact callback is the installed sink," but the `OFF` level short-circuits and returns `Success` without installing any sink or consuming the once-only init slot — contradicting the stated invariant, which the file/stderr sibling had guarded with an explicit "(or skipped for level OFF)" clause.
  **Rule:** For process-wide first-call-wins init C-ABI functions where a `Success` code can mean either "installed against your request" OR "intentionally skipped/no-op" (e.g. level OFF), the return-value contract MUST spell out the skip case in every entry point, or a host believes a sink is live when nothing was installed.

### 2026-08-25: learnings since 2026-08-24T07:40:03Z
- **Context:** PR #289 added `kernel_session_config_set_tls_client_certificate()` to the C ABI, taking the mTLS client cert and private key through a single setter (both required, both copied before return, either null/empty → InvalidArgument) rather than two independent setters.
  **Rule:** For C-ABI config values that are only valid together (cert+key, id+secret, endpoint+scope pairs), expose them through one atomic setter so a partially-configured state is unrepresentable at the FFI boundary; validate all parts non-null/non-empty before mutating the config.
- **Context:** PR #289 verified the full C-ABI mTLS path without a live workspace or committed credentials: a hermetic E2E test generates a CA + server + client identities at runtime (rcgen/rustls), and a unit test passes PEM with valid framing but invalid contents so client construction fails at the parser — proving both values traversed C ABI setter → TlsConfig → reqwest without any network I/O.
  **Rule:** Test TLS/credential-forwarding paths hermetically — generate CA/identities at runtime instead of committing keys, and prove config reached the client by feeding framing-valid/content-invalid PEM so the failure lands in the parser (before network I/O), asserting on that specific error rather than requiring a live endpoint.

### 2026-08-26: learnings since 2026-08-25T07:31:52Z
- **Context:** PR #291 aligned `Metadata::type_info()` with the Thrift `getTypeInfo` corpus. A review bot repeatedly flagged `CHAR`/`VARCHAR` `CASE_SENSITIVE=false` as inconsistent with `STRING=true` (vanilla HiveServer2 `Type.isCaseSensitive()` marks all three case-sensitive), and the engineer-bot "fixed" them to `true` several times — the maintainer reverted each time, confirming Databricks Thrift actually returns `STRING=true`, `CHAR=false`, `VARCHAR=false`.
  **Rule:** Databricks Thrift metadata (e.g. `getTypeInfo` CASE_SENSITIVE) diverges from vanilla HiveServer2 semantics; never "correct" a synthesized metadata cell to match reference/vanilla behavior without confirming against a real Databricks server response — an apparent internal inconsistency may be the correct, intended divergence.
- **Context:** PR #291's `type_info` tests asserted the synthesized `getTypeInfo` output against literals hand-derived from the same `SparkGetTypeInfoUtil`-style synthesis logic; reviewers noted a wrong-but-consistent cell would still pass, and the parity claim couldn't be enforced offline without live-warehouse credentials.
  **Rule:** A test that checks synthesized results against values re-derived from the same code proves self-consistency, not parity with the real server — enforce a "matches <server>" claim with a golden fixture captured from a live server, and name the test/doc for what it actually locks (self-consistency) so the claim isn't overstated.
- **Context:** PR #288 matched on the float literal `0.0` (`Some(0.0) => ...`) in the pyo3 bindings when treating zero as "keep default".
  **Rule:** Matching on a floating-point literal triggers rustc's `illegal_floating_point_literal_pattern` future-incompat lint, which is promoted to a hard error under the repo's `-D warnings` gate; compare with `==` in a match guard or `if` instead of using a float literal pattern.
- **Context:** PR #288's clippy failure lived in the `pyo3/` crate, which declares its own `[workspace]`, so the repo's root `cargo clippy --all-targets` never covered it and the error could slip through the gate.
  **Rule:** Standalone-workspace subcrates (e.g. `pyo3/`) are NOT covered by the root `cargo clippy`/`cargo test` invocation — run clippy and tests from within each standalone-workspace directory explicitly, or lint/test failures there pass CI silently.
- **Context:** PR #288 exposed `request_timeout` to Python/C; the binding docs (echoing the pre-existing `src/config.rs` field doc) claimed it caps one request "from connect through response-body completion," but it is applied as reqwest's `read_timeout` (src/session.rs), with a separate 30s `connect_timeout`.
  **Rule:** The kernel's `HttpConfig::request_timeout` is a reqwest `read_timeout` — it bounds the gap between successive reads and resets on each read; it does NOT cap connection establishment nor total body-download time. Document and reason about it as a read-idle timeout, not a total request deadline.
- **Context:** PR #283 (U2M OAuth token-cache control); a reviewer flagged that caller-supplied token stores keyed on `host` alone would diverge from the built-in `DiskTokenCache`, whose cache filename is a SHA-256 of `{host, client_id, scopes}`.

### 2026-08-28: learnings since 2026-08-27T10:33:31Z
- **Context:** PR #303 removed the `session_conf` allowlist so caller keys forward verbatim; review flagged that a caller-set `can_cloud_download` now reaches the wire.
  **Rule:** SEA accepts a `can_cloud_download` session conf at CreateSession but rejects it at the *first* ExecuteStatement with `CONFIG_NOT_AVAILABLE`, poisoning every subsequent statement on the session — disable CloudFetch per-statement via the SEA `disposition` field (matching JDBC/Thrift), never via a session conf.
- **Context:** PR #303 dropped the case-sensitive `spark.*` conf handling when removing the allowlist.
  **Rule:** Dotted `spark.*` Spark conf keys are case-sensitive and must be sent verbatim (lowercase-dotted) — unlike SET-style SQL params (e.g. `ANSI_MODE`) which the server echoes uppercase; uppercasing a Spark key addresses the wrong `SQLConf` entry and is silently ignored server-side.
- **Context:** PR #301 mapped an empty catalog filter to `(None catalog, empty LIKE pattern)` for `list_schemas`/`list_columns` to mean "match nothing."
  **Rule:** In metadata_v0, `catalog = None` means "ALL CATALOGS" (the opposite of match-nothing), so an empty-catalog request only stays empty because the empty-pattern short-circuit fires first — keep that ordering dependency explicit or an empty catalog silently broadens to every catalog. Empty schema/table/column LIKE patterns also short-circuit to an empty result with no wire call.
- **Context:** PR #293 narrowed retryable-vs-permanent DNS detection by string-matching reqwest's error source chain (reqwest exposes no typed DNS variant).
  **Rule:** Classifying DNS failures by lowercased message substrings is platform-fragile — glibc, macOS, Windows, and musl/Alpine (`EAI_NONAME`) each phrase NXDOMAIN differently; a permanent-failure marker set that omits musl phrasings will retry a non-existent host until the whole retry budget is burned. Cover every target libc's phrasing.
- **Context:** PR #293's transport-retry tests spawn a mock server task that calls `accept()` a fixed N times, then end with `server.await`.
  **Rule:** A mock-server test that accepts a fixed number of connections then awaits the server task will *hang* (surfacing only via CI global timeout, with no useful message) if a regression makes the request non-retryable and fewer connections arrive — assert the observed accept count before awaiting the handle, or wrap the client call / `server.await` in a `tokio::time::timeout` so a missing retry fails fast.
- **Context:** PR #287 added a per-session telemetry circuit-breaker whose `CircuitBreakerManager` is a process-global `OnceLock<HashMap<host, Arc<CircuitBreaker>>>` populated with `or_insert_with`.
  **Rule:** A process-global cache keyed only by host and filled with `or_insert_with` makes the first session's config win permanently — later sessions' per-session knobs are silently dropped and breaker open/closed state leaks across sessions and across tests sharing a mock host. Key on `(host, config)` (or document first-writer-wins), and give tests unique hosts to avoid shared-state coupling.
- **Context:** PR #287's `valid_config` rejected a zero `circuit_breaker_timeout` unconditionally, while the threshold check was gated on `circuit_breaker_enabled`.
  **Rule:** Gate validation of a sub-feature's tuning knob on that sub-feature's enable flag — an ungated check (rejecting a zero timeout even when the breaker is disabled) lets a benign unused value disable the whole parent feature (all telemetry), a footgun that only bites direct-Rust callers since binding validators reject the value up front.
- **Context:** PR #287 moved the pyo3 crate's `extension-module` feature out of the default set so `cargo test` links correctly.
  **Rule:** Keep PyO3's `extension-module` feature OFF for plain `cargo test`: it intentionally suppresses libpython linking for extension modules on Unix, which breaks the Rust test binary (undefined Python symbols). Enable it only for maturin wheel builds (via `pyproject.toml`), where the loading interpreter provides the symbols.
- **Context:** PR #274 deferred the success telemetry event until the result stream is exhausted/dropped, but async paths still called `finalize(None)` eagerly on success; review found metrics dropped and errors mis-reported as success.
  **Rule:** When statement finalization is guarded by a one-shot `finalized: AtomicBool` shared across cloned handles, the first finalize wins and all later ones are silent no-ops — so an eager success-finalize on any path defeats a deferred finalize (dropping stream/CloudFetch metrics), and a post-attach fetch error unwound through `Drop` gets exported as success with `error = None`. Ensure exactly one finalize site owns the terminal event and that error paths finalize before the stream is dropped.
- **Context:** PR #274 records CloudFetch `initial_chunk_latency` from concurrently-downloaded chunks.
  **Rule:** Under concurrent chunk downloads a first-to-complete gate (e.g. `compare_exchange(-1, …)`) records the fastest/smallest chunk's latency, not chunk 0 — gate `initial_chunk_latency` strictly on `chunk_index == 0` to match the JDBC/C# `initialChunkLatency` semantic. Also keep an explicit completed-download counter so a stream dropped before any download finishes reports `None`, not a misleading `Some(0)` (both `slowest`/`sum` atomics init to 0).

### 2026-08-29: learnings since 2026-08-28T10:54:51Z
- **Context:** PR #299 and PR #306 added telemetry-finalizing `close(&mut self)` inherent methods on `ExecutedStatement`/`ExecutedAsyncStatement` alongside the existing `ExecutedStatementHandle::close(&self)` trait method; the reviewer showed that with the trait in scope (or via `Box<dyn ExecutedStatementHandle>`), `exec.close()` silently resolves to the non-finalizing `&self` trait method, reintroducing the telemetry gap — the napi/pyo3 sites only worked because they used UFCS (`Type::close(&mut …)`).

### 2026-09-03: learnings since 2026-09-02T07:30:13Z
- **Context:** PR #310 added a per-call deadline to `kernel_session_test`; a reviewer caught the deadline-elapsed error being built with `Error::new(ErrorCode::Timeout, …)` instead of the categorised `Error::timeout()` constructor. `Error::new` defaults `retryable = false`, whereas every other kernel `Timeout` (`Error::timeout()`, `Error::from_http_status(504)`) is `retryable = true`, so retry wrappers that branch on `Error::retryable` would treat it inconsistently.

  **Rule:** The outbound `User-Agent` prefix is functionally load-bearing — the SEA server gates response disposition on it via a prefix allow-list, so any change to the base UA (or a caller-supplied UA that replaces it) must use a prefix registered in `known_driver_prefixes`, or requests silently lose parallel chunk downloads / fall back to Thrift.

### 2026-09-04: learnings since 2026-09-03T07:29:10Z
- **Context:** PR #312 added a detached result-stream canceller for the C ABI. A reviewer caught that `kernel_result_stream_canceller_new` formed a whole-struct `&ResultStreamInner` via `.as_ref()` while `next_batch` held a whole-struct `&mut` via `.as_mut()` across the fetch — documented as a blessed concurrent-access pattern, but UB. Fix projected each hot path to disjoint fields via `addr_of!`/`addr_of_mut!`.
  **Rule:** In FFI handles shared across threads, never materialize a whole-struct `&mut`/`&` (`.as_mut()`/`.as_ref()`) held across an await/fetch when another thread may take ANY reference to the same allocation — `&mut` carries a noalias guarantee over the ENTIRE allocation, so "each side only touches disjoint fields" is sound at the field level but still UB at the reference level; project to the specific field via `std::ptr::addr_of!`/`addr_of_mut!` instead.
- **Context:** PR #312's headline concurrency test (`cancel_interrupts_an_in_flight_next_batch`) originally obtained the canceller BEFORE spawning the fetch thread, so the concurrent-obtain-during-in-flight-next_batch path the docs explicitly bless was never actually exercised; it was reworked to obtain the canceller AFTER the fetch thread parked inside `next_batch`.
  **Rule:** A test that claims to cover a documented concurrent/racing path must sequence its operations so the second call genuinely overlaps the in-flight first one (e.g. obtain/fire the racing handle only after the worker thread has parked mid-operation) — otherwise it exercises the sequential case and the blessed race is untested; also flag which arm/shape a shared code path is actually driven by, since a mirror arm can be structurally similar yet never hit.
- **Context:** PR #312's per-stream `CancellationToken` interrupts an in-flight `next_batch` via `tokio::select!`, but it is intentionally not wired into the CloudFetch provider's own `cancel_token`; the provider awaits a spawned download's `JoinHandle`, so firing the token drops the `next_batch` future at its await point without aborting the detached download.
  **Rule:** Dropping a future at an await point only bounds the CALLER'S wait — it does not abort work the future was merely awaiting on a spawned task (`JoinHandle`); a client-side cancellation signal gives a bounded caller-return, not reclamation of the in-flight request/connection, so for true bounded teardown either wire the signal into the underlying provider's cancel token or close the resource to release it on its own completion, and document the distinction.

### 2026-09-06: learnings since 2026-09-05T07:24:56Z
- **Context:** PR #322 fixed a CloudFetch consumer that looped forever when an initial or incremental link fetch failed. A link fetch fails *before* any `ChunkEntry` exists for the requested chunk and leaves `end_of_stream` unset, so a waiter blocked in `wait_for_chunk` has nothing in `chunks` to observe and no terminal signal.
  **Rule:** When a failure can occur *before* the per-item entry a waiter keys off exists, record it in a provider-level terminal-error slot (first-writer-wins to preserve original SQLSTATE/source) and wake all waiters — a per-entry error path alone leaves waiters for the not-yet-created entry looping forever.
- **Context:** In PR #322 a reviewer caught that the provider-level `terminal_error()` check in `wait_for_chunk` was placed *before* the ready-chunk check. Because the download frontier runs ahead of the consumer by up to `max_chunks_in_memory`, chunks between the consumer position and the failed page are often already downloaded; checking terminal-error first discarded that valid buffered data.
  **Rule:** Check requested-item readiness BEFORE surfacing a stream-level terminal error, so already-downloaded in-order items are still delivered; the terminal error should only fire once the consumer reaches the item that actually failed — mirror the per-item failure path's ordering.
- **Context:** PR #322's `set_terminal_error` used tokio `Notify::notify_waiters()`, which only wakes waiters already registered when it fires. The `wait_for_chunk` loop constructed its `notified()` future inline in the `select!` *after* the terminal-error/readiness checks, leaving a window where a notification could be missed and the consumer stalled until `chunk_ready_timeout` (30s default).
  **Rule:** With tokio `Notify::notify_waiters()`, construct and `.enable()` the `notified()` future BEFORE the state/terminal checks at the top of the wait loop — registering it inline after the checks (in the `select!`) races the notification and can stall a waiter until the timeout fires.
- **Context:** PR #322's `incremental_link_fetch_failure_is_terminal` test claimed to cover the incremental link-fetch path but let chunk 0 fail via the unrelated per-chunk download path and only asserted `Err(_)`, so it would pass even if the new logic were broken. The fix served chunk 0's bytes from a wiremock server with a real downloader (so it succeeds) and asserted the surfaced error carried the injected message + SQLSTATE.
  **Rule:** A test that only asserts `Err(_)` cannot distinguish which failure source fired; when validating a specific error path, make every *other* path succeed (e.g. serve real bytes via mock) and assert the error's identity (message/SQLSTATE), not just its presence.

### 2026-09-07: learnings since 2026-09-06T07:25:25Z
- **Context:** PR #323 bounded CloudFetch chunk downloads with an end-to-end deadline by setting reqwest's per-request `.timeout()` to the remaining budget; a reviewer noted this *overrides* rather than composes with the client-wide `request_timeout`.
  **Rule:** reqwest's per-request `.timeout()` REPLACES the client-wide `.timeout()`, it does not take the min — when narrowing a per-attempt deadline always apply `min(client_request_timeout, remaining_budget)` yourself, or a larger configured budget silently loosens the static per-request safety net.
- **Context:** PR #323's HTTP retry loop rebuilds the request on each attempt; the reviewer/author found a per-request timeout set by the caller was dropped because the rebuild fell back to the client-wide `.timeout()`.
  **Rule:** Any per-request setting (timeout, headers, body) must be captured before a retry loop and re-applied on every rebuilt request — reqwest request reconstruction does not carry caller-set per-request state forward across attempts.
- **Context:** In PR #323 a chunk state machine stored failures as `ChunkState::DownloadFailed(String)`, so the typed `Error`'s `ErrorCode::Timeout` was lost and the consumer path re-wrapped it as `Error::io()`; tests that asserted on the function's direct return value passed while the consumer still observed `ErrorCode::Io`.
  **Rule:** Preserve the typed `Error` (not a stringified copy) through state machines and channels so `ErrorCode` classification survives to the consumer/C-ABI boundary — and assert error classification on the path a real caller observes (e.g. `wait_for_chunk`/`next_batch`), not on the internal function's direct return, which gives false confidence.

- **Context:** PR #316 fixed an aarch64 handshake failure against a private/internal CA: `tls-rustls = ["reqwest/rustls-tls"]` resolves to webpki-roots (Mozilla bundle) only, while the `tls-native` (OpenSSL) builds read the OS `/etc/ssl` trust store.
